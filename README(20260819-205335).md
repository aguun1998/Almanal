# ALMANAL

**A bounded, evidence-aware control framework for algorithm synthesis, optimization, verification, and recursive improvement.**

> Current release candidate: **ALMANAL 14.30**  
> Reference runtime: **0.30**  
> Status: **SUCCESSOR CANDIDATE / NOT CANON**

ALMANAL is not a collection of competitive-programming tricks, a prompt template, or a benchmark-specific optimizer. It is a control framework for making a reasoning system search less, commit later, verify stronger claims with stronger evidence, and optimize the final artifact on an explicit non-scalarized Pareto frontier.

The framework is designed around a simple principle:

> **Find the right representation early, eliminate work before measuring time, require evidence for strong state transitions, and stop when further reasoning no longer repays its cost.**

The compact contract can be used directly with a capable reasoning model. A dependency-free Python reference runtime is provided for executable semantics, conformance checks, experimentation, and auditability.

---

## Why ALMANAL exists

A strong model can often solve an algorithmic problem, yet still waste substantial effort in one or more of the following ways:

- exploring too many equivalent representations;
- implementing candidates that could have been rejected analytically;
- treating an optimistic estimate as achieved performance;
- benchmarking before structural work has been minimized;
- continuing to optimize after the useful frontier is already closed;
- accepting self-declared completion, verification, or capability claims;
- improving one axis while silently regressing another;
- finding the correct asymptotic algorithm but stopping before reducing the residual execution state, arithmetic, memory traffic, or I/O bottleneck.

ALMANAL makes these failure modes explicit control problems.

For algorithm/code tasks, the default protected floor is semantic correctness and constraint/stability compliance. Above that floor, the default optimization target is a **non-scalarized Pareto vector** led by:

- runtime, when actually measured;
- structural execution work;
- peak live memory;
- source/code bytes;
- produced artifact bytes;
- secondary structural costs such as passes, allocations, memory accesses, materializations, and portability/dependency burden.

Exact wall-clock time is never inferred from structural work. Structural work can prove a directional optimization; milliseconds require measurement.

## Core execution model

The current compact control path is approximately:

```text
freeze task / baseline / criterion / protected invariants / resource axes
        |
        v
cheap representation race (<= 4 abstract families)
        |
        v
bounded active beam (default <= 2)
        |
        +--> static infeasibility / external-frontier rejection
        |
        v
proof-obligation bundling + pre-implementation footprint
        |
        v
validated Representation Lock
        |
        v
materialize only the surviving small frontier
        |
        v
witnessed residual execution-compression closure
        |
        v
one ordinary finalization pass
        |
        v
benchmark only if unresolved empirical outcome can still change selection
        |
        v
baseline-dominance / Pareto gate
        |
        v
STOP
```

Several details are deliberate.

### Representation before implementation

ALMANAL races a small number of abstract mechanisms before producing multiple coded variants. A useful representation is preferred when a single invariant closes several obligations at once: necessity, sufficiency, construction/decision, and complexity.

A candidate must carry an explicit mechanism, feasibility, mandatory obligations, and a nonnegative reasoning-work bound. Unknown reasoning cost is not treated as zero.

### Static Pareto screening before benchmarks

Candidates are screened using analytic cost models before implementation whenever possible. A benchmark is not used to discover what a proof or exact structural count can already settle.

Optimistic candidate bounds are scheduling hints, not elimination evidence. An unwitnessed candidate cannot kill another unwitnessed candidate merely because its optimistic lower bound looks better.

### Representation Lock is not optimization termination

Once a mathematical representation is locked, ALMANAL performs one bounded **Residual Execution Compression** audit when performance/resource axes are material:

```text
minimal sufficient dynamic state
-> transition-native representation
-> repeated transition-class aggregation
-> narrow-common / sparse-exception storage when proved
-> proved arithmetic narrowing / delayed reduction
-> structurally material selective specialization
-> local I/O audit when the core has become cheap
```

This distinction matters. A correct `O(N)` representation may still contain avoidable state, reductions, branches, materialization, or I/O overhead.

### Benchmark last

Benchmarking is reserved for residual environment-dependent questions. It is not a substitute for proof, static rejection, or operation-count analysis.

Hardware-specific intrinsics, `mmap`, special syscalls, large custom parsers, or compiler-target tricks are not resident defaults. They must repay their source, memory, portability, and maintenance rent under the task's frozen objective.

## Evidence and strong-state discipline

ALMANAL separates planning metadata from evidence.

```text
SelfDeclaredMetadata != WitnessedProperty
NoCounterexampleFound != Proof
StructuralWorkDown != ExactMillisecondsDown
SchedulingPriority != EvidenceWeight
ConvergenceSTOP != GlobalOptimalityProof
```

Strong transitions such as Representation Lock, witnessed residual completion, extra finalization, reserve reopening, and post-lock falsifier work fail closed unless their evidence requirements are satisfied.

ALMANAL 14.30 specifically hardens these paths:

- Representation Lock is validated before it can dominate alternatives.
- Residual completion requires validated evidence for every bounded audit class.
- A caller cannot bypass residual validation with a completion boolean.
- Even a resource-immaterial skip is evidence-bound.
- Extra finalization, reserve reopen, and post-lock falsifier work require a fresh validated witness.
- Fresh witnesses are consumed through a run-scoped serialized ledger; the same witness cannot repeatedly refresh a lease.
- Caller-supplied counters cannot reset ordinary-finalization or reserve-reopen budgets.
- Arithmetic narrowing checks the complete proved intermediate interval, not only an upper bound.
- Benchmark-last prerequisites fail closed when omitted.

The framework intentionally refuses to turn every low-level planning hint into a heavyweight certified object. The current convergence point preserves that boundary.

## DDC, SCA, and Feedback

ALMANAL is recursively audited using three complementary modes.

### DDC

DDC is used adversarially: search for concrete fail-open paths, self-attestation, unsafe convergence transitions, invalid dominance, stale traceability, or other contract violations. Repairs are localized and admitted only when a concrete counterexample or material defect exists.

### SCA

SCA treats the framework itself as an optimization target. It attempts to delete, merge, compile away, move cold, or generalize redundant machinery while preserving protected semantics and evidence boundaries.

`SourceSmaller != SystemSimpler`; a reduction is retained only when it does not reopen a previously closed defect.

### Feedback

Deterministic defects are handled before empirical experiments. Feedback stops when the remaining direction has insufficient evidence or expected material value to repay lifecycle complexity.

For 14.30, the final DDC/SCA/Feedback cycle stopped after no further local fail-open, self-attestation, or unsound-elimination counterexample was found without introducing a broader host/session subsystem.

This is a **local convergence stop**, not a claim of global optimality.

## Using ALMANAL with a reasoning model

The simplest mode is contract-driven use.

1. Provide `ALMANAL_14.30.md` to the model as task context.
2. State the task and the optimization criterion explicitly.
3. Ask the model to use ALMANAL as the governing control contract.
4. If code/artifact optimization matters, provide the baseline or request that one be frozen before variants are generated.
5. Require actual measurements only for claims that depend on the execution environment.

A compact instruction is sufficient:

```text
Use ALMANAL_14.30.md as the governing reasoning/control contract for this task.
Freeze the task, protected correctness/stability constraints, baseline, and relevant
Pareto axes before generating variants. Prefer representation-level simplification,
static rejection, and structural-work reduction before benchmarking. Do not treat
self-declared metadata or unmeasured wall time as evidence. Stop when the remaining
frontier has no evidenced material improvement worth its complexity cost.
```

For algorithm synthesis, it is often useful to add:

```text
Target the unconstrained best algorithm first. Do not prematurely optimize for human
memorability or textbook familiarity. Before implementation, race a small number of
representations and estimate structural work, peak live memory, source complexity,
and I/O. After Representation Lock, run the residual execution-compression audit once.
```

ALMANAL does **not** require the model to expose private chain-of-thought. The intended outputs are decisions, proofs or proof sketches where appropriate, cost models, artifacts, verification results, and scoped claims.

The Python runtime is an executable reference implementation of the control semantics. It is not the only permitted backend.

Requirements:

- Python **3.11+**
- no third-party runtime dependencies

### Install the runtime

```bash
unzip ALMANAL_RUNTIME_0.30.zip -d almanal-runtime
cd almanal-runtime
python -m pip install -e .
almanal demo
```

```bash
python -m almanal_runtime demo
```

## AtCoder ARC227 post-contest benchmark campaign

ALMANAL has been exercised on archived **AtCoder ARC227** problems as a practical algorithm-synthesis and optimization benchmark.

The goal was not merely to obtain AC solutions. The workflow compared plain-model solutions, ALMANAL-guided solutions, and strong human submissions on correctness, execution time, memory, and source size, then fed concrete failures back into the framework.

This campaign produced new high-ranking post-contest submissions on the historical ranking/submission views. Selected observed results include:

| ARC227 task | ALMANAL-guided result | Notes |
|---|---:|---|
| C | **220 B / 1 ms / 1664 KiB** | Representation collapsed to the primitive-period quotient; extremely small state and artifact |
| D | **341 B / 4 ms / 4016 KiB** | Majority closure reduced to pairwise literal compatibility; source/time strong, memory remained a tradeoff |
| E | **327 B / 5 ms / 2360 KiB** | GF(2) polynomial -> odd-part 2-adic chains; final optimization identified I/O as the residual bottleneck |

For task E, the first compact ALMANAL submission was approximately `289 B / 12 ms / 2460 KiB`. After the residual-compression pass, the mathematical core was intentionally left unchanged and only the material I/O bottleneck was addressed. The resulting `327 B / 5 ms / 2360 KiB` submission was, at the time it was observed, **the fastest displayed submission except for two C implementations**.

This is an important example of the framework's intended behavior: learning a new optimization technique does not imply applying it. Transition-class aggregation and deeper specialization were considered, but rejected when their source-complexity rent did not repay itself for this instance. A lightweight parser survived the Pareto screen because it attacked the actual remaining bottleneck.

The ARC227 results should be interpreted as **observational task-level benchmark evidence**, not as proof that ALMANAL is globally superior to every plain-model, human, compiler, or architecture configuration. AtCoder rankings, runtimes, compiler behavior, and visible submission sets are environment- and time-dependent.

## A few algorithmic patterns discovered or reinforced during ARC227

The benchmark campaign was also used to refine reusable search principles.

### Proof-obligation bundling

Prefer a representation that closes several mandatory obligations at once over one that repeatedly reopens necessity, sufficiency, construction, and complexity as separate searches.

### Pre-implementation footprint estimation

Before coding, estimate the candidate's structural work, live memory, source/artifact burden, and material I/O. A candidate with unknown costs should not look artificially attractive merely because its costs were omitted.

### Experiment as falsifier

Small exhaustive searches, randomized checks, or property tests are most valuable when they cheaply attack a high-leverage structural hypothesis. Passing a non-exhaustive experiment is not promoted to proof.

### Minimal sufficient dynamic state

After finding the correct mathematical representation, ask whether the transition system itself can be represented with less state. A set, interval, table, or DP may collapse to a constant-width sufficient statistic.

### Transition-class aggregation

When many independent components share a proved transition signature, count component classes and evaluate them in bulk instead of replaying the same recurrence individually.

### Narrow common case, sparse exception

When safe and profitable, use a narrow dense representation for the common range and a sparse side structure for rare overflow/exception values.

### Proven arithmetic narrowing

Delay modular reduction or use smaller arithmetic only after proving the complete intermediate range. Convenience is not a proof of safety.

### Structure before microarchitecture

Remove states, transitions, passes, allocations, materialization, and unnecessary I/O before considering SIMD, `mmap`, architecture pragmas, or other machine-specific techniques.

## What ALMANAL is not claiming

ALMANAL 14.30 deliberately keeps the following claims out of scope unless independently evidenced:

- that it is globally optimal;
- that convergence-stop proves no better framework exists;
- that structural-work reduction numerically predicts wall-clock latency;
- that self-checking is equivalent to independent verification;
- that a compact source artifact is automatically a better system;
- that the reference Python runtime is the only valid implementation;
- that the ARC227 benchmark establishes universal behavioral superiority.

The current release evidence explicitly records independent behavioral superiority as **NOT_TESTED**.

## Design philosophy

ALMANAL favors mechanisms that make strong systems **less wasteful and harder to fool themselves**:

- freeze identity and objectives before observing outcomes;
- preserve correctness and stability as hard floors;
- separate scheduling heuristics from evidence;
- use proofs and exact structural counts where they dominate experiments;
- use experiments only when empirical uncertainty remains decision-relevant;
- prefer a small Pareto frontier over premature scalarization;
- keep STOP as an explicit competitor;
- treat the framework's own reasoning cost, residency, source size, and maintenance burden as optimization targets;
- refuse architecture growth unless an existing composition is demonstrably insufficient.

The intended endpoint is not maximal deliberation. It is **minimum sufficient deliberation that still produces the best evidenced artifact available under the frozen objective and resource budget**.

## Current status

**ALMANAL 14.30 is a successor candidate, not canon.**

The 14.30 cycle reached a local DDC/SCA/Feedback convergence stop after the remaining hardening ideas required broader host/session ownership machinery without a demonstrated material local defect or Pareto gain. Future revisions should reopen that decision only when new evidence, a concrete counterexample, or a materially better design direction appears.
